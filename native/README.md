# Native mod

The same mod as a native Horizon mod: [horizon-mixins](https://github.com/horizon-rust/horizon-mixins) bundles
whose hooks are compiled into Horizon itself, so it builds on an unmodified Horizon. The mod's logic is `src/`,
unchanged; this folder holds the game-side hooks and the tooling around them.

| Path | What |
|---|---|
| `mixins/spider_man/` | **The shipped bundle**, pinned to Horizon's Nightly of 2026-11-08 (`native/compatibility.json`; `native/dev/compatibility.json` pins the local dev commit `socket-commit.sh` made on top of it). Generated by `tools/release.sh`: don't edit it by hand |
| `dev/mixins/spidey-socket/` | The game-side hooks, the source the bundle is generated from (`socket.rs` + helpers + manifest) |
| `dev-reload/` | Development only: the "socket" the dev game loads the mod through, reloaded when rebuilt; `abi.rs` is the data the hooks and the mod exchange each tick |
| `sdk/` | The mod SDK's surface (`horizon_mod_sdk`) served from that data, so `src/` builds unchanged |
| `plug/` | `src/` built as the library the dev game loads |
| `tools/` | `release.sh`, `release.py`, `package.py` (the registry's `.hnmod`), `dev-build.sh`, `socket-commit.sh`, `watch.sh`, `horizon.py` (staging, adapted from horizon-native-mod-template) |

## Hooks

| Hook | Horizon function | Does |
|---|---|---|
| HEAD | `game::remote::Game::tick_remote` | each tick: rays, keys, the player to the mod; velocity, fall reset, pose, camera, shake, wind, chat lines, the web shot's sound and the first-swing hint back |
| HEAD + RETURN | `game::remote::Game::remote_send_state` | while the mod forgets the fall, your own world's server hears you as on the ground (never another server) |
| HEAD | `game::leads::Game::leash_geometry` | the web strands |
| cancellable HEAD | `game::perspective::Game::player_model_geometry` | the posed player model (third person) |
| cancellable HEAD | `game::perspective::Game::camera_view` | chase and fixed camera |
| cancellable HEAD + a `pub` module | `horizon_client_render::camera::view_matrix`, module `spider_man_view` in `horizon-client-render/src/camera.rs` | the wall camera's turn of the whole view, for the frame's own yaw and pitch (world, culling, sky, reflections) |
| HEAD, hook points | `native_command`, `native_commands` | `/swingmode …` goes to the mod (own world only), listed and completed in the chat box |
| HEAD, hook points | `native_mods`, `native_settings`, `native_settings_click` | the mod's row in Options > Mods: its keys (rebindable, read with `native_mod_key`), the web delay, the on/off switch (`native_on`) |
| HEAD, hook point | `native_camera_shake` | the rumble, scaled by Distortion Effects |

The mod acts only in your own world (single player, or a LAN world you host): Horizon's own server thread is
running and the game is connected to it. Numbers from the mod that are not finite are dropped, ray offsets are
bounded, and a panic in the mod skips its tick (it starts over) instead of crashing the game.

## Differences from the WebAssembly version

- While posed, the player model is drawn without armour, the held item or elytra.
- The help shows in chat, not a HUD panel; the mod's panel is one line, the hint for a first web or zip, shown as
  the action bar for up to a minute a session. The settings file is `mod-storage/spider-man/` in the game's folder
  (`hint=done` there once a web was shot or a zip made; delete the line to see the hint again).

## Install with the Horizon launcher

Native mods are not sandboxed: the mod's code runs with your rights, so read `mixins/spider_man/` first. Tested on
macOS and Windows 11 with launcher 0.2.31–0.2.37.

- **From the registry**, once listed: Mods > search "Spider-Man" > Install.
- **From GitHub**: Mods > Add from GitHub with `https://github.com/wyddy7/minecraft-spider-man-rust` (its latest
  release's `.hnmod`), or `horizon-launcher mods add-github https://github.com/wyddy7/minecraft-spider-man-rust
  --trust-native-code`.
- **From a clone**: `horizon-launcher native-build minecraft-spider-man-rust/native/mixins/spider_man
  --trust-native-code`.

The launcher prepares the pinned Nightly's resources from your own Minecraft 26.3 if it hasn't
(`horizon-launcher prepare --version <it>`), then builds; the first build downloads its own Rust and Horizon's
source and takes a few minutes (about 27 on a low-power Windows laptop). Preparing needs Minecraft 26.3: sign in
with the Microsoft account that owns it and the launcher downloads it (and its Java); without that it needs Java 25
on the PATH. Tested on macOS and Windows 11. Press F5 for third person, hold R and jump.

## Build the shipped mod from source

Beside this repository: a Horizon clone containing the pinned commit and
[horizon-mixins](https://github.com/horizon-rust/horizon-mixins) at the revision in `compatibility.json`.
Rust 1.95 (from `rust-toolchain.toml`), Python 3.12 via [uv](https://docs.astral.sh/uv/).

```sh
native/tools/release.sh                 # regenerate mixins/spider_man/, stage and build
native/tools/release.sh --generate-only # regenerate only
uv run --python 3.12 python native/tools/package.py   # native/target/spider_man-<version>.hnmod
```

The client is printed at the end; run it with your prepared resources (`--resources`). Players use the launcher
instead (above).

## Release a version

1. Bump `version` in `dev/mixins/spidey-socket/horizon-mixin.toml` and add a CHANGELOG section.
2. `tools/release.sh` (regenerates `mixins/spider_man/` and builds it), then play it: swing, a wall run, the mod's
   page in Options > Mods.
3. `uv run --python 3.12 python native/tools/package.py` writes `target/spider_man-<version>.hnmod`;
   `cargo horizon-mod check <it>` (the `cargo-horizon-mod` built from the pinned Horizon) must pass.
4. Pull request to `main`, then a GitHub release (not a pre-release) tagged `v<version>` with the `.hnmod` as its
   asset. Horizon's registry pins every version by its SHA-256 (`mods/spider_man.toml` in horizon-mods), so a release
   alone does not reach the launcher's Mods page: add the version through the form at
   `playhorizon.dev/mods/submit` (signed in as an owner of the entry), which opens a pull request there; a reviewer
   reads it and merging publishes it.
5. Check the player's path: `horizon-launcher mods add-github https://github.com/wyddy7/minecraft-spider-man-rust
   --trust-native-code`, then `horizon-launcher native-build --trust-native-code`, then play.

## Move to a newer Horizon

1. Pick a Nightly and its source tag (`nightly-source/<date>-<short>` in Horizon). The horizon-mixins revision is the
   launcher's own at that commit: `MIXINS_REV` in `launcher/src/native_mods.rs`. Check out horizon-mixins there.
2. Write both revisions into `compatibility.json` (and the `game.rs` SHA-256 of that commit; `mixin_schema` as the
   template's). Check that every hook target in `dev/mixins/spidey-socket/horizon-mixin.toml` still exists, and look
   for new hook points in `crates/horizon-client/src/game/native_hooks.rs` that could replace a hook.
3. `tools/release.sh` until it builds; then `tools/socket-commit.sh` and `tools/dev-build.sh` for the development
   loop on the same commit (and pin `dev/compatibility.json`'s horizon-mixins revision to the same one).
4. Play both builds, then release as above.

## Develop with live reload

```sh
native/tools/socket-commit.sh   # once per Horizon pin: a local Horizon commit with the socket crate
native/tools/dev-build.sh       # the dev client (about 2–3 minutes; sound on)
native/tools/watch.sh           # leave running: rebuilds the plug when src/ changes
HORIZON_DEV_PLUG=native/target/debug/libspider_man_plug.dylib  # then start the dev client with this set
```

Edit `src/` (a number in `spidey.rs`, a pose), save: the running game uses it within about a second. A change to
the hooks or to `dev-reload/abi.rs` needs `dev-build.sh` and a restart; a change to the socket crate also needs
`socket-commit.sh`. The mod's state starts over on each reload (a swing in progress drops).

`HORIZON_TARGET=<dir>` reuses a Cargo target directory between builds (a Horizon build is several GB).
