# Native mod

The same mod as a native Horizon mod: a `.hmod` whose [horizon-mixins](https://github.com/horizon-rust/horizon-mixins)
rows patch copies of Horizon's own functions, built by the launcher against a prebuilt game, so it runs on an
unmodified Horizon. The mod's logic is `src/`, unchanged; this folder holds the game-side hooks and the tooling
around them.

| Path | What |
|---|---|
| `hmod/` | **The shipped mod**, a `.hmod` project pinned to Horizon's Nightly of 2026-11-18 (`compatibility.json`). Generated by `tools/hmod.py`: don't edit it by hand |
| `hmod-src/lib.rs` | The mod's crate inside `hmod/`: its keys, `/swingmode`, the web delay row and the fall hook through Horizon's mod API, and the state the game-side copies share |
| `mixins/spider_man/` | The intermediate bundle `tools/release.sh` generates (the game-side module with `src/` inlined, and the rows), which `tools/hmod.py` turns into `hmod/` |
| `dev/mixins/spidey-socket/` | The game-side hooks, the source both are generated from (`socket.rs` + helpers + manifest) |
| `dev-reload/` | Development only: the "socket" the dev game loads the mod through, reloaded when rebuilt; `abi.rs` is the data the hooks and the mod exchange each tick |
| `sdk/` | The mod SDK's surface (`horizon_mod_sdk`) served from that data, so `src/` builds unchanged |
| `plug/` | `src/` built as the library the dev game loads |
| `tools/` | `release.sh`, `release.py`, `hmod.py`, `dev-build.sh`, `socket-commit.sh`, `watch.sh`, `horizon.py` |

## Hooks

| Kind | Horizon function or hook | Does |
|---|---|---|
| HEAD | `game::remote::Game::tick_remote` | each tick: rays, keys, the player to the mod; velocity, fall reset, pose, camera, shake, wind, chat lines, the web shot's sound and the first-swing hint back |
| HEAD, AFTER_CALL | `game::remote::Game::remote_send_state`; after its calls in `tick_remote_player` and `tick_local_player` | while the mod forgets the fall, your own world's server hears you as on the ground (never another server) |
| HEAD | `game::prediction::Game::guest_replay` | the start of a player's turn on your own world's server: is it you, with a web holding? |
| `living_fall` (mod API) | Horizon's fall hook | while your web holds, your own player's landing does no damage; everyone else's is untouched |
| HEAD | `game::leads::Game::leash_geometry` | the web strands |
| cancellable HEAD | `game::perspective::Game::player_model_geometry` | the posed player model (third person) |
| cancellable HEAD | `game::perspective::Game::camera_view` | chase and fixed camera |
| cancellable HEAD | `horizon_client_render::camera::view_matrix` | the wall camera's turn of the whole view, for the frame's own yaw and pitch (world, culling, sky, reflections) |
| HEAD | `game::native_hooks::base::Game::native_camera_shake` | the rumble, scaled by Distortion Effects |
| mod API | `register`, `register_client_commands`, `command`, `setting_changed` | R and Z in Controls, `/swingmode` (own world only), the web delay on the mod's page |

The mod acts only in your own world (single player, or a LAN world you host): Horizon's own server thread is
running and the game is connected to it. Numbers from the mod that are not finite are dropped, ray offsets are
bounded, and a panic in the mod skips its tick (it starts over) instead of crashing the game.

## Differences from the WebAssembly version

- While posed, the player model is drawn without armour, the held item or elytra.
- The help shows in chat, not a HUD panel; the mod's panel is one line, the hint for a first web or zip, shown as
  the action bar for up to a minute a session. The settings file is `mod-storage/spider-man/` in the game's folder
  (`hint=done` there once a web was shot or a zip made; delete the line to see the hint again).

## Install with the Horizon launcher

Native mods are not sandboxed: the mod's code runs with your rights, so read `hmod/` first. Needs launcher 0.2.70
or later; tested on macOS with 0.2.78.

- **From the registry**, once listed: Mods > search "Spider-Man" > Install.
- **From GitHub**: Mods > Add from GitHub with `https://github.com/wyddy7/minecraft-spider-man-rust` (its latest
  release's `.hmod`), or `horizon-launcher mods add-github https://github.com/wyddy7/minecraft-spider-man-rust
  --trust-native-code`.
- **From a clone**: `horizon-launcher native-build minecraft-spider-man-rust/native/hmod --trust-native-code`.

The launcher prepares the pinned Nightly's resources from your own Minecraft 26.3 if it hasn't
(`horizon-launcher prepare --version <it>`), then builds: it downloads the prebuilt game and its mod tools once,
and compiles only the mod (seconds after that). Press F5 for third person, hold R and jump.

## Build the shipped mod from source

Python 3.12 via [uv](https://docs.astral.sh/uv/), and `cargo horizon-mod` built from the pinned Horizon
(`cargo install --locked --git https://github.com/horizon-rust/horizon --rev <horizon_revision> cargo-horizon-mod`).

```sh
native/tools/release.sh --generate-only               # regenerate mixins/spider_man/ from the sources
uv run --python 3.12 python native/tools/hmod.py      # write hmod/, pinned as compatibility.json says
(cd native/hmod && cargo horizon-mod build)           # native/hmod/target/horizon-mod/spider_man.hmod
horizon-launcher native-build native/hmod --instance <instance> --trust-native-code
```

## Release a version

1. Bump `version` in `dev/mixins/spidey-socket/horizon-mixin.toml` and add a CHANGELOG section.
2. Build as above, then play it: swing, a wall run, the mod's page in Options > Mods.
3. Install the packed `.hmod` the way a player does (copy it into the instance's `horizon-native-mods/`, then
   `horizon-launcher native-build --instance <instance> --trust-native-code`) and play that build.
4. Pull request to `main`, then a GitHub release (not a pre-release) tagged `v<version>` with the `.hmod` as its
   asset. Horizon's registry pins every version by its SHA-256 (`mods/spider_man.toml` in horizon-mods), so a release
   alone does not reach the launcher's Mods page: add the version through the form at
   `playhorizon.dev/mods/submit` (signed in as an owner of the entry), which opens a pull request there; a reviewer
   reads it and merging publishes it. Put the pinned-build report (the Horizon commit it was built and played on) in
   the release notes and the form: the registry asks for it. Its check builds on the newest Nightly, so send the
   form the day of the release.
5. Check the player's path on a fresh instance: `horizon-launcher mods add-github
   https://github.com/wyddy7/minecraft-spider-man-rust --trust-native-code`, then `horizon-launcher native-build
   --trust-native-code`, then play.

## Move to a newer Horizon

1. Pick a Nightly and its source tag (`nightly-source/<date>-<short>` in Horizon). `cargo horizon-mod new probe
   --template native --horizon <build>` shows the horizon-mixins revision that build pins.
2. Write both revisions into `compatibility.json`. Check that every row in `dev/mixins/spidey-socket/horizon-mixin.toml`
   still names a function in the build's function index (`functions.json` of the launcher's prebuilt package; a
   function whose body has a macro or a `cfg` is refused), and look for mod API hooks that could replace a row
   (`cargo horizon-mod hooks <words>` in `hmod/`).
3. Build until it compiles; play it, then release as above.

## Develop with live reload

Not moved to the `.hmod` Nightly yet: the loop below runs on the earlier Nightly its pins name.

```sh
native/tools/socket-commit.sh   # once per Horizon pin: a local Horizon commit with the socket crate
native/tools/dev-build.sh       # the dev client (about 2–3 minutes; sound on)
native/tools/watch.sh           # leave running: rebuilds the plug when src/ changes
HORIZON_DEV_PLUG=native/target/debug/libspider_man_plug.dylib  # then start the dev client with this set
```

Edit `src/` (a number in `spidey.rs`, a pose), save: the running game uses it within about a second. A change to
the hooks or to `dev-reload/abi.rs` needs `dev-build.sh` and a restart; a change to the socket crate also needs
`socket-commit.sh`. The mod's state starts over on each reload (a swing in progress drops).

`HORIZON_TARGET=<dir>` reuses a Cargo target directory between builds (a Horizon build is several GB).
